Roadmap

Audited against the source rather than against prior documentation. The absent rows are here for the same reason as the shipped ones: you should be able to decide against this engine using its own documentation, and find out on day one rather than in week three.

Last audited 2026-11-07. Since the previous audit, more work landed outside this plan than inside it — cloth, volumetric fog, decals, weather, water, GPU particles, screen-space reflections, multi-view rendering and the frame profiler all ship today. Nine rows below that used to read Absent were describing a repository that no longer exists, so the baseline was rewritten rather than appended to. The unplanned work gets its own section, because a roadmap that quietly absorbs whatever happened cannot be used to argue about what should happen next.

The full working document lives in the repository as Roadmap.md, with the dependency reasoning behind every ordering decision. This page is the public summary of it.

One fact that sets the cost of several items above. The pipeline is forward rendering — pipeline states are organised as Opaque / Transparent / Fade with cull variants, with a storable depth target, a velocity target and — since the normal target landed — a second colour attachment. There is still no G-buffer. That is why decals are a screen-space pass instead of a deferred one, and why reflections read the normal target instead of reconstructing normals from depth.

What it cost. Every one of those landed as a new four-language shader set: one driver plus HLSL, GLSL, MSL and WGSL sources. The shader corpus grew by roughly sixty percent since the previous audit, and the four languages stay within a few percent of each other in size. That is the honest price of each backend owning its own shader — and it is the argument for Track P, which attacks the boilerplate around the shaders rather than the shaders themselves.

How the work is grouped

Work is grouped into tracks that map to the questions the project actually faces. Ordering inside each track is by dependency, not by appeal — several attractive features sit late because their prerequisites are infrastructure work across four backends.

TrackQuestion it answers
A. RenderingIs the renderer genuinely next-gen?
B. Host & worldsCan someone see what the engine does without reading the source?
C. AIIs the paid layer worth money, and does it help make games?
D. FoundationsCan any of the above be proven, maintained, or shipped?
F. Agent surfaceCan a person and an agent drive the same engine through one command surface, without a bespoke API for either?

Track A — Rendering

The list was sound; the execution went further than the list. Ten of the original thirteen items are shipping code today. The three that are not need something outside this track: a build pipeline, an asset pipeline, and a recorded baseline. So this section is no longer a plan — it is a status table, with the design record kept only where it still explains a decision.

What the shipped rows actually say.

  • Indirect draw landed on all four backends, including Metal and WebGPU, which the previous ordering expected to trail behind a capability flag. It had to land before culling: without it, "GPU culling" means compute a mask, read it back, issue CPU draws — a stall, and usually slower than the CPU frustum culling already shipping.
  • The normal target paid for itself twice. GTAO stopped reconstructing normals from depth, and SSR and the decal pass read the real thing. Depth-derived normals are flat-shaded per triangle and lose all normal-map detail, which survives ambient occlusion and does not survive reflections or decals. Doing SSR first and adding the buffer afterwards would have meant writing the resolve twice.
  • Volumetric fog shipped beyond scope — it shadows the volume against punctual lamps, so a lamp in a valley casts a shaft and not just a glow — and it is the effect that justifies the CPU reference implementation pattern: FogMath.cs is why four shader implementations can be checked against one another at all.
  • GPU-driven culling is built and unproven. It compacts per-instance bounds into five slots with original-index indirection, and it sits behind a SEASON_CULL_INDIRECT switch built for an A/B that has not been run. That switch is not caution; it is the admission that without a recorded baseline there is no way to show the GPU path is faster. At ten thousand entities in a managed engine the bottleneck is more likely per-entity Update cost than draw submission — and if so, A7 is the wrong fix.
  • A10 is the half of A7 that was not built. Occlusion culling is absent, and the most frequently misread file in the repository is the one that makes people think otherwise: HiZ.cs is SSR's acceleration structure, not an occlusion test. A10 should consume that same pyramid rather than build a second one.

The four original open items are not rendering features: each is an asset pipeline, a measurement, or an optimisation that has to be justified by one — which is why A8 and A9 sit behind the measurement layer rather than in front of it. The four rows added above (A11–A14) are not features either. They are the structural debt that ten visual features in one year produced, and they are the four places where the next ten would slow down.

Track B — Host and shareable worlds

An editor is a demonstration surface, not the workflow. It exists so the renderer can be seen. It does not exist to become the way the engine is used.

  • B0 — decouple the shell from the scene. Today Create() builds the whole island unconditionally. "Run with no world loaded" and "create a new world" are the same capability, and everything else in this track needs it first.
  • B1 — world serialization. The design rule comes before the format.
  • B2 — editing affordances. Undo first, then placement, gizmos, a property editor over construction parameters only, and hierarchy inspection — because the command stream F0 defines is an undo log, which turns undo from the last item into the first requirement.
  • B3 — asset catalogue, with licence attribution as a required column, because bundled assets travel with shared worlds.
  • B4 — a second reference world: mass unit scheduling. Tens of thousands of independently updated, individually animated units, instrumented from the start. It doubles as the benchmark A7 requires.

The anti-fragmentation contract. A serialized world record is a C# type name plus construction parameters. It is never a bag of properties with attached behaviour fragments. Layout is data; behaviour is code; the boundary is the type name. That single constraint is what keeps this from becoming an inspector-assembled component model.

World tierContentsShareable as a file?Who can open it
Static worldBuilt-in types only, plus bundled assetsYesAnyone with the app
Code-bearing worldReferences project-defined typesNo — share the C# projectAnyone with the source

That distinction has to be explicit in the format and visible in the UI, or the project inherits the exact dependency problem it is trying to avoid: a shared world that silently fails to load because a type is missing.

Track C — AI

Since the previous audit this track split in two: the generation layer moved out to the repository root and became twelve libraries plus a studio app, and what is left here is the part that was always the point — getting generated output into a scene.

  • C1 — generated output into the engine. Partial. A generated mesh can be previewed inside an engine control, which is the first slice. Missing: generated image to material texture, to 2D sprite, generated audio to a playable source, a stable generated-assets folder — and the reverse direction, pick an object and send its current texture to image-to-image as the reference. Small work, and still the highest return on effort in the whole roadmap.
  • C2 — cloud models plus runtime C# generation, desktop only. This is now the highest-value item in the track, because Track F depends on it. Half the transport exists — upload, download, progress, cancellation — but not streaming completion and not key storage; and the Roslyn host that compiles C# at runtime does not exist at all. The architecture is already shaped to receive the result: a behaviour is a Panel or Control subclass, so a generated class only has to be instantiated and added — no serialization format to satisfy, no component model to register with.
  • C3 — 3D asset generation. The easy half shipped. SeasonAIs/SeasonThreeD is a Trellis runner: prompt to mesh, observed working. What is missing is every downstream step — mesh decimation, UV unwrapping, normal repair and a glTF exporter. The model was never the hard part.
  • C4 — automatic rigging. Research, not a commitment. It will not appear on a store listing before output quality is verified against real characters.

C2 comes before C3, which inverts the intuitive order — and the practice only half-disagreed, by shipping C3's model first. The argument still holds. C2 is an HTTP client plus a Roslyn host; what remains of C3 is a mesh pipeline plus an exporter. C2's quality is supplied by frontier models and improves for free; C3's is capped by what local 3D models produce and by post-processing nobody has written. And C2 exploits something this engine has and its competitors do not — behaviour as a single compilable C# class.

Runtime C# compilation is unavailable under full AOT, which rules out iOS and WebAssembly. That constraint is stated rather than worked around: the feature is desktop-only by nature.

Track D — Foundations

Every item here is either a prerequisite for proving a claim in another track, or a prerequisite for the project surviving contact with contributors.

  • D1 — benchmarks and image-diff regression. Half built. The four rulers exist as tools: a layout freeze over material parameter structs, a draw-order trace, frame capture with a pixel diff, and a CPU cost profile. What does not exist is the part that turns four tools into a gate — recorded numbers against a fixed camera path, and CI that runs them on a commit. For a project whose pitch is the renderer is real, a silent visual regression is the most expensive possible bug, and the failures this codebase actually accumulates — per-frame buffer cross-talk, uncleared atlas memory, struct layout drift, shader divergence between four APIs — are exactly the kind a compile check never catches.
  • D2 — frame allocation budget. Measured, not yet a budget. The profiler records allocation bytes and Gen0/1/2 counts every frame, so the instrument exists. What is missing is the contract behind it: a recorded number on a fixed scene, and a check that fails when it moves. Pure C# engines are dismissed on exactly one axis, GC pauses, and that will appear in the first community thread. The answer cannot be prose. "Zero bytes allocated per frame at ten thousand animated instances" ends the argument in one line; nothing else does.
  • D3 — asset pipeline, absorbing texture compression, LOD generation, mesh decimation and import caching. The runtime must keep loading plain glTF and plain PNG directly: the pipeline is an optimisation, never an entry requirement.
  • D4 — documentation and a sample ladder. A minimal BaseApp under 50 lines, one-concept samples, and a written walkthrough for adding a compute effect — currently the most contributor-friendly extension point in the engine, and discoverable only by reading Ddgi.cs.
  • D5 — platform honesty. No fallback paths. Features declare requirements, unsupported features are visibly disabled with a stated reason, and the backend matrix is generated from the same source.

Track F — Agent surface and the lightweight editor

This track exists because of one property the engine already has and most engines it is compared against do not: a behaviour here is one C# class, and a world record is a type name plus construction parameters. No component model, no inspector-configured behaviour, no prefab graph to satisfy. An agent does not need to understand an editor to drive this engine — it needs to emit a class, name it, and place it.

The second reason is cheaper to state and harder to argue with: an agent is the only realistic way to keep a demonstration honest. Every release needs the island, the weather, the fog, the cloth and the water to still look right on four backends, and a person clicking through that is a person who will eventually stop. A replayable command stream with a screenshot diff behind it is the difference between a demo and a regression suite.

F0 — one command surface, two clients. A design rule, not a feature:

Every editor action is a command. The agent is a second client of the same command stream. There is no agent-only API and no UI-only mutation path. If a person can do it, the agent calls the same command; if an agent does it, the editor shows it and can undo it.

  • Undo is promoted. It stops being "late" and becomes the command layer's first requirement, because a command stream is an undo log.
  • Objects need addresses, not references. The picker returns a live object today; a command needs a stable id that survives a save and a reload. That falls out of B1's type registry, not out of a new system.
  • Every command needs a dry run. The agent proposes a diff, a person reads it, and only then does it apply — the same shape as git diff, and the reason this track is not "give the model the keyboard".
  • The editor is not the API. If the shell is the only client, the API grows shell-shaped: modal state, selection, focus. Two clients from day one keeps it honest.

Safety, stated plainly. No network listener by default: stdio, or a localhost socket with a token in a file the user can see — a control surface that can spawn objects and compile code is remote code execution if it is ever bound to 0.0.0.0. Generated code runs with full application trust, because it is a normal C# class in the normal app; there is no sandbox, so consent is per session, visible and revocable. And the agent never gets a capability the UI lacks — not a security property, an auditability one: if a command could do something a person could not, there would be no way to review it.

What this changes elsewhere: B2's undo moves first, D1 stops being optional, and C2 is promoted from "the paid layer's next step" to "Track F's enabler". Nothing about the non-goals changes — the agent writes the same C# class a person writes, which is the only reason any of this is defensible.

Track P — Performance and build economics

Everything here answers one question: does the frame budget hold on the hardware the audience actually owns, and can the answer be shown rather than asserted. It is separate from Track A because none of it is a rendering feature, and separate from Track D because it is not about proving the project works — it is about making it fast and small.

  • P0 — measurement on all four backends, first. The profiler is real, but the GPU timer interface has exactly one implementation, Direct3D 12. The GPU column is empty on Vulkan, Metal and WebGPU — the three backends where a managed engine's frame budget actually needs defending, because that is where the integrated GPUs and the browsers are. Timestamp queries per backend, plus an explicit "unsupported" state instead of a silent NaN. Until this lands, every item below can only be argued.
  • P1 — contract code generation. The graphics interface is roughly seventy-five methods implemented by hand four times. Backend similarity runs from about 30 % to 90 % per object family, and the low end is D3D12-specific logic, not extractable duplication — so the realistic saving is three to five thousand lines, not the six to eight a similarity ratio suggests. The real payoff is that the four implementations cannot drift apart silently.
  • P1b — struct and constant mirroring. A smaller generation problem sitting next to P1, and easy to mistake for it. The frame-wide constant block is 2464 bytes and is mirrored by hand into four shader languages and, in one web file, into a single hardcoded byte length. Every other size in the system is derived, so that constant is the one place where a layout change fails silently — the upload is simply discarded, with no error on either side. Ordered after the block split, because generating headers for one unsplit struct would document the problem rather than reduce it.
  • P2 — shader precompile and PSO disk cache. All four backends compile at startup and nothing survives a restart: D3D12 has no pipeline library, Vulkan persists no pipeline cache. A content-addressed cache on disk, keyed by source hash plus pipeline state, with the runtime compilers still present as fallback — an optimisation, never an entry requirement, so a fresh clone still runs with an empty cache.
  • P3 — texture compression and a KTX2 container, formerly A0.3. BC7/BC5/BC6H on desktop, ASTC on mobile, ETC2 as the Android floor, one file for every platform. Its payoffs are package size, web load time, VRAM and bandwidth — none of which is a picture, all of which are the difference between a browser build someone waits for and one they close.
  • P4 — temporal upscaling and dynamic resolution. TAA already owns everything an upscaler needs: jittered history, a velocity buffer, variance clipping, a resolve. A TAAU-style upscale from 67 % or 50 % is a small increment on an effect that works, and the largest single GPU win on integrated hardware. Build it against a fixed scale and measure it first; a dynamic resolution controller without a profiler behind it oscillates, and P0 is what stops that.

Most of these are invisible in a screenshot, and the order is set by the item that makes the others measurable rather than by the one that looks best in a release note.

Track E — VR / XR

The single-view objection that used to open this section is gone. The per-view split shipped: view and projection are per view, the frame state carries per-view camera and lighting snapshots, per-view targets, up to eight views in one frame — and the sample app already renders rear-view mirrors through the same path. That was the expensive half, and it was paid for while the scene pass was open for other reasons.

What still blocks VR is the part that was never prepaid: no OpenXR binding, no stereo submission, no per-eye pacing. The frame loop still paces on window vsync, input is pointer-only, and the UI is screen-space. This track stays last because it is a new platform claim, not a feature on the existing one.

Priority layers

A layer is a dependency band, not a date. Everything in L0 can start today; nothing in L1 can finish before its L0 dependency lands. L2 and L3 are deliberately undated, because what they cost depends on how L1 lands. Track P keeps its own P0–P4 item numbers — the layers use L so the two are never confused.

L0 — Make the claims measurable

  • D1 recorded numbers and CI — a fixed camera path, per-feature toggles, the four acceptance rulers run by a commit
  • P0 GPU timers on Vulkan, Metal and WebGPU — coverage goes from one backend of four to four of four
  • A ten-thousand-instance stress scene, because A7 cannot be judged on the island
  • A7 proved or demoted against that scene, using the switch that already exists
  • D2 allocation budget and D6 the build guard

Outcome: every row below cites a number instead of an intention, and one feature is decided rather than carried.

L1 — Make the world data

  • B0 shell and scene decoupling, then B1 world serialization
  • F0 the command layer with undo first, then F2 the world verbs and F1 headless capture
  • A12 split the frame-wide constant block, then P1b generate the shader-side declarations from it
  • P1 contract code generation and the shared middle core, in three steps
  • A13 material assets and instances
  • Asset pipeline and texture compression as one project, including the decimator
  • C1 completion and D4 the sample ladder

Outcome: a world is a file, an agent can drive it, a person can undo it, and a texture costs a quarter of what it did.

L2 — Renderer architecture and the agent loop

  • A11 one frame instance instead of a static facade
  • A14 streaming and asynchronous upload, keyed on material identity
  • A10 occlusion culling on the depth pyramid that already runs for SSR
  • P4 temporal upscaling, then dynamic resolution on top of the profiler
  • C2 cloud models plus Roslyn runtime C#
  • P2 shader precompile and PSO disk cache

Outcome: the frame path has no static state, the first launch is not a compile, and an agent can extend the engine rather than only drive it.

L3 — Scale, tools, and new audiences

  • A8 mesh LOD, then A9 terrain, then B4 the mass-unit reference world
  • C3 mesh post-processing and glTF export
  • B2 editing affordances, B3 asset catalogue, F3 agent tools, F4 the four-pane editor
  • Track E, then Quest — a new platform claim, not a feature on the existing one
  • Physics and networking, recorded and deliberately not ranked
  • Console technical adaptation — acknowledged, scheduled nowhere

Outcome: the strategy-scale claim is measured, and the editor is a view over commands that already work.

Three things this ordering changes.

  • A7 moved to the front. A feature that exists, is switchable and has never been measured is worse than a feature that does not exist, because it gets quoted in the README. Deciding it costs one A/B run.
  • Undo moved out of the editor and into the command layer. A command layer without undo is an API with extra steps, and a world format that stores references cannot be made undoable afterwards — which is why the world record has to carry addresses from the first commit.
  • Texture compression and the asset pipeline merged, as did contract code generation and the shared middle core. Each pair was two rows in two tracks and was always one project.

Non-goals

A roadmap without these is a wish list. Each of the following is a decision, not an omission.

  • Competing on feature count with editor-centric engines.
  • Visual scripting, node graphs, or inspector-assembled behaviour, in any form.
  • A generalised frame graph before the fixed schedule is genuinely limiting.
  • Runtime texture compression, or any decode-to-uncompressed path.
  • A centralised template or asset marketplace.
  • Rebuilding around ECS for trend alignment. If bulk entity updates prove to be the bottleneck, the answer is a targeted data-oriented path for bulk entities, not a paradigm change across the engine.
  • Fallback rendering paths. Capability reporting instead.
  • Any XR runtime besides OpenXR — the same rule that killed OpenGL fallbacks.
  • Console certification or store policy as engine work. Porting the engine is the vendor's side of the line; certifying a shipped game is the developer's.
  • An agent-only mutation API, or a control surface bound to a network interface by default. One command surface, two clients — and the agent never gets a capability the editor lacks.
  • A second shader toolchain. Code generation wraps the shaders; it never generates them. Each backend keeps its own hand-written source, because that independence is the one architectural decision that has paid for itself repeatedly.
  • A second depth pyramid, or a separate occlusion hierarchy, while SSR's already runs every frame.

How to tell whether this is working

  • The renderer claim is provable: benchmark numbers and reference images are published, not described.
  • The GC objection is answerable in one number.
  • Someone can evaluate the engine in ten minutes without reading engine source.
  • Generated assets end up in scenes, not in a folder.
  • Adding a world type does not require writing editor code.
  • Season/ stays smaller and clearer than the feature list would suggest.
  • One implementation per domain still holds — no OpenGL fallback appears, no second animation format, no second text renderer.
  • Every editor action is also a command, and every command can be undone.
  • The GPU profile column is populated on all four backends for the same scene, so "it got faster" is a measurement rather than a memory.
  • Adding a visual feature stops costing four driver files of boilerplate. The shaders stay four; the plumbing around them does not.
  • When Track E starts, the same rule extends to XR: OpenXR only, no runtime-specific integration layers.

Disagreements about ordering are welcome and useful. Open an issue — the reasoning in Roadmap.md is written down so it can be argued with.
